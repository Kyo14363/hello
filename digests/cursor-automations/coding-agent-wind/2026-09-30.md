1. **來源：** [論壇 173367](https://forum.cursor.com/t/cli-agent-cannot-use-mcp-servers-that-are-connected-in-desktop/173367)（Colin 21:05Z；回報者 21:18Z 確認）  
   **主張：** Desktop Settings → MCP 顯示 Connected，不代表 CLI Agent 能用。兩邊**分開存登入**；CLI 目錄會把同一台機器上的伺服器標成 `needsAuth`、tool 清單空的，agent 也不能自己開 OAuth（會回「只能在 desktop IDE」）。正解是在該專案目錄跑 `agent mcp list`，再對每個未 ready 的名字執行 `agent mcp login <name>`（或 session 內 `/mcp` → Login）。登入是**依專案資料夾**存的，換 repo 可能要再登一次。現場：Desktop 3.22.12（`3a92974`）＋ CLI `2026.09.28-64d2043`。  
   **為什麼值得記：** 「MCP 已連上」只描述 Desktop。CLI／headless 演示前先 `agent mcp list`，不要以為同一台電腦會共用 token。

2. **來源：** [論壇 173352](https://forum.cursor.com/t/grok-4-7-subagents-fall-back-to-auto/173352)（kevinn 18:24Z）＋ [論壇 173272](https://forum.cursor.com/t/sonnet-5-5-subagents-route-to-auto/173272)（mohitjain 08:24Z）  
   **主張：** 主 chat 用 **Grok 4.7** 時，第一層 subagent **實際跑 Auto**，卡片卻可能仍寫 Grok 4.7 Extra High；巢狀層才把 Auto 露出來。Explore Subagent Model **只管內建 Explore**，coordinator／developer 繼承主 chat，handoff 就在這裡被換成 Auto。同一帳號上 Grok 4.6 Extra High 能把每一層留在 4.6（標籤「High Fast」不可信）。**Sonnet 5.5** 在 desktop 也是同一條：subagent 真的跑 Auto；問模型自己是誰不算證據，看卡片或 [usage](https://cursor.com/dashboard/usage)。Workaround：主 chat 改 4.6，或把 `.cursor/agents/*.md` 的 `model:` 釘成 Sonnet 5／Opus 5.5，不要 `inherit`。員工說 **CLI 與 Cloud Agents 不受影響**。  
   **為什麼值得記：** 「指定 Grok 4.7／Sonnet 5.5 帶一隊 subagent」今天在 IDE 不成立。比模型、報成本前先對 usage，不要信標籤或模型自述。

3. **來源：** [論壇 173276](https://forum.cursor.com/t/cloud-agents-mini-probes-pass-eng-shaped-implement-prompts-die-at-kickoff-3-msg-0-tools-2026-09-28/173276)（mohitjain 09:01Z；回報者 13:42Z 確認）  
   **主張：** 「小 probe 過、實作 prompt 開機即死（約 3 句、0 tool）」不是 prompt 長度或 MCP。失敗 run 用 **7 字短 SHA**，通過的用 default branch；Cloud Agent start **解析不了短 commit**，規劃完就停。解法：`starting_ref` 用分支，或 `git rev-parse` 的 **40 字完整 hash**。回報者改 `starting_ref=main` 後 tools 跑起來（bc-31f1fc5b…）。這是程式化啟動才會踩到的後端限制，status 當時顯示 Operational。  
   **為什麼值得記：** API／腳本不要傳短 SHA。現場「Cloud Agent 一規劃就死」先對 starting ref，不要當模型或環境壞了。

4. **來源：** [論壇 173369](https://forum.cursor.com/t/cloud-environments-github-repo-renaming-issues/173369)（kevinn 23:43Z，員工自測）  
   **主張：** Cloud Environment **記住建立時的 repo 名**，GitHub rename 後 clone／push／開 PR 靠 redirect 還能過，但更新 PR 會被拒：`PR URL must belong to the current repository`。Environment 與 Project **都不能改綁 repo**，只能新建。Workaround：更新既有 PR 時給**舊名完整 URL**（`github.com/org/old-name/pull/123`），員工測過會打到改名後的 repo；只給 branch 名仍失敗。新工作另開 environment。  
   **為什麼值得記：** 改過 GitHub 名的 repo，不要演示「用新 URL 更新 PR」。Project 也換不了 environment。

5. **來源：** [論壇 173345](https://forum.cursor.com/t/cursor-sdk-local-agents-shell-ignores-local-cwd-and-runs-in-the-host-processs-cwd/173345)（Colin 16:52Z，員工 repro）  
   **主張：** `@cursor/sdk` 1.0.31／1.0.32 的 `Agent.create({ local: { cwd } })` 裡，檔案工具與 transcript 用 `local.cwd`，**Shell 預設卻是 host `process.cwd()`**。模型沒帶 `working_directory` 時（Opus 5.5 第一下常漏），會讀到／提交到 **主進程目錄**。SDK 還把 `processWorkingDirectory: process.cwd()` 傳給模型。回報者強制不帶 cwd 時，gpt-5.6-sol／composer-2.5／Sonnet 5.5／Opus 5.5 **全部**落到 host。Workaround：每個 agent 一個 `child_process.fork(..., { cwd: workspace })`，或把 host 開在空目錄。  
   **為什麼值得記：** 同進程併發 local agent 可能寫錯 repo。演示 SDK 前先 `pwd; cat MARKER.txt`，不要只信 `local.cwd`。
