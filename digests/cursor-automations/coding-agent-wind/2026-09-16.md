3. **員工確認：Agent 的 Stop 只停當前回合，已派出的 subagent／長指令會繼續並把 agent 叫醒**  
   來源：[論壇 171659](https://forum.cursor.com/t/agent-chat-stop-unpredictable-and-broken/171659)（deanrie 9/15 07:36 UTC）  
   主張：Stop 結束當前回合；已經丟到背景的 subagent 或 terminal 長指令會跑完，然後把 agent 喚醒，看起來像 Stop 被忽略。輸入框上方有 Working pill 時，要開它按 **Stop All**，或直接在 terminal 停指令。員工在追這條。另一條「Stop 把可見回覆捲回上一則」不該在已產出回覆後發生，另案追。回報者之後貼了沒按 Stop 也靜默捲回的 Request ID，尚未被員工定性。  
   為什麼值得記：任何「按 Stop 就安全停下」的演示，先問有沒有 Stop All、背景 subagent 是否還在燒額度。

4. **員工確認：3.20.21 在 WSL 還原後，`gatherTerminalSelections` 會把 Agent 卡死在本機**  
   來源：[論壇 171663](https://forum.cursor.com/t/agent-hangs-forever-on-taking-longer-than-expected-in-gatherterminalselections-after-wsl-terminal-restore-cursor-3-20-21/171663)（mohitjain 9/15 09:23 UTC）  
   主張：卡住的 follow-up **根本沒離開本機**，不是帳號／模型問題。Reload Window 能解卡住的視窗，但會把舊 remote host 留在 WSL；要清乾淨需先存檔，再 **完全退出 Cursor + `wsl --shutdown`**。帶 terminal chip 的那則聊天寫在歷史裡，reload／shutdown 清不掉——編輯第一則拿掉 chip 再送，或開新聊天；貼純文字輸出可避開。  
   為什麼值得記：這是可複測的 IDE agent 卡死，不是雲端過載。WSL 工作區看到「Taking longer than expected…」先查 terminal chip，不要先怪模型。
