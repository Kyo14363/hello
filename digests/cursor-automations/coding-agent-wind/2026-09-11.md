# coding-agent-wind｜2026-09-11

官方硬更新來了：Cursor Projects 上線，把「每件事開一個 chat」換成常駐 coordinator，但「幾千個 subagent／重度用戶合併 PR 六倍」仍是第一方數字，窗口內可核對的員工回覆反而在講編排器會被 300K 續跑與佇列偷窺卡住。

1. **Cursor Projects：官方 beta，coordinator 自己不寫碼，雲端跑、關筆電不停**  
   來源：[changelog](https://cursor.com/changelog/projects)、[產品文](https://cursor.com/blog/projects)、[@cursor_ai 2098162488013455784](https://x.com/cursor_ai/status/2098162488013455784)（9/10 21:31 UTC；截稿前約 4.6k 讚、425k 曝光、194 引用）  
   主張：左側欄開 Project，跟單一持久執行緒裡的 coordinator 說話；它只規劃、委派、把成品交回檢查。預設跑在自己的雲端機，關筆電不停；要在本機測才拉起 local agent。共享檔會在雲端／本機機之間同步（研究、產物、測法、偏好）。Subscriptions 可看 Slack、排程、跟 PR／CI。官方寫「可委派到數千個 subagent、上下文撐好幾個月」；文內第一方數字是新用戶合併 PR +30%、以 Projects 為主的用戶 6 倍、設計系統 Project「朝每天 20–100 個 PR」。標成 beta、即日起對所有用戶滾動。公開 docs 路徑 `/docs/projects` 目前 404，只有 changelog／blog。  
   為什麼值得記：這是自 9/2 Self-hosted machines 以來第一則產品級 changelog，直接改「coding agent 的工作單元」。6 倍／數千個還沒有獨立複測，先當行銷主張。

2. **員工用法：更新 app 才看得到；一個 Project ≠ 一個 repo；現有 chat 可拖進去**  
   來源：作者 [alexirobbins](https://x.com/alexirobbins/status/2098200587787718893)（00:02 UTC：更新 app；[23:33](https://x.com/alexirobbins/status/2098193153597776197) 對 Kent：Projects 偏寫碼、Grok Bot 偏知識工作）、[poteto 2098165460714057863](https://x.com/poteto/status/2098165460714057863)（內測「用它出過幾千個 PR」、coordinator + pstack 可編幾百甚至幾千個 agent）、[2098186080839475568](https://x.com/poteto/status/2098186080839475568)（當 chat 資料夾、可把側欄舊 chat 拖進 Project）、[2098197278465077323](https://x.com/poteto/status/2098197278465077323)（同一 app 可拆 perf／新功能多個 Project）  
   主張：滾動不是「登入就有」，要先更新。員工自己不當成一倉一 Project，而是一條活一個 Project。pstack 要先 `/setup-pstack` 選便宜模型。Kieran Klaassen 另寫雲端已能 `/multitask`（[引用帖](https://x.com/kieranklaassen/status/2098178896500064702)），尚未見員工複述。  
   為什麼值得記：這是窗口內唯一接近可驗證演示的員工操作說明；「幾千個 PR／幾千個 agent」仍是當事人自述，不是公開 repo 對賬。

3. **編排器實作：員工確認 subagent 背景終端續跑會把 1M 窗打成 300K**  
   來源：[論壇 171263](https://forum.cursor.com/t/cursor-resets-subagent-model-context-windows-mid-run/171263)（kevinn 9/10 16:08 UTC）  
   主張：`.cursor/agents` 裡設 1M 的 Sonnet 5 subagent，正常回合用滿 1M；一旦背景跑終端、完成後自動 resume，那一回合改用 300K，既有上下文大於此就觸發摘要。不是使用者配錯。權宜：subagent 定義寫死前景執行並等結束。回報者問「這樣 orchestrator 幾乎不能 resume 已有上下文的 subagent」；第三人補：前景換掉並發，長 watcher 也不適用，交接前要把契約／決策寫進耐久檔。  
   為什麼值得記：官方同一天在賣「coordinator 派幾千個 agent」；員工同窗口承認長跑委派會在 resume 路徑被截窗。這是對 Projects 敘事最硬的限制，不是論壇氣氛。

4. **轉向／佇列：員工確認 agent 會偷看未送出的 follow-up 並提前動手**  
   來源：[論壇 171197](https://forum.cursor.com/t/agent-is-acting-on-queued-messages-before-they-are-sent/171197)（mohitjain 9/10 09:23 UTC）  
   主張：Agents Window 3.19.13 上，agent 會呼叫看 queue 的工具、讀到你預寫、還沒送出的 follow-up，邊做當前任務邊開工；真訊息稍後仍會再送一次，變成做兩遍。員工說不該這樣、已在追。權宜：規則寫「不要看／不要動 follow-up queue」；要立刻做就按 Send now。  
   為什麼值得記：官方把「不打斷轉向、佇列等到下一個 tool call」寫進 8/19 harness；Projects 又加排程／Slack 喚醒。若 queue 對模型可見，長任務的「先排後做」不可靠。
