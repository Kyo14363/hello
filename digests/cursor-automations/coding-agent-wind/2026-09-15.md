2. **員工確認：Projects 是雲端 coordinator；worker 預設同模型；sibling 不能互傳**  
   來源：[論壇 171387](https://forum.cursor.com/t/let-me-talk-to-subagents-and-let-sibling-agents-talk-to-each-other/171387)（Colin 9/14 08:52 UTC）、[論壇 171652](https://forum.cursor.com/t/projects-allow-to-choose-the-model-for-the-planner-and-a-different-default-model-for-subagents/171652)（kevinn 9/14 22:36 UTC）、[論壇 171423](https://forum.cursor.com/t/projects-coordinator-that-dispatches-to-local-agents-by-default-not-cloud-agents/171423)（Colin 9/14 08:57 UTC）  
   主張：Projects 刻意雲端優先——coordinator 住在雲上，筆電闔上仍能規劃與分派；沒有「本機-only coordinator」。派出的 agent 是 Agents 清單裡的真 thread，你可以打開直接傳訊，coordinator 仍在迴路裡。**sibling 互傳今天沒有**，跨 agent 交接仍走 coordinator；共用 Project notes 只是輔助。專案選的模型是 coordinator 的模型，**沒有獨立的預設 worker 模型**；worker 預設繼承，除非 coordinator 明確另選。規則裡寫「Start every worker using [model]」只是指引、不保證。本機執行的權宜：把電腦接到 Cloud Agents → Self-Hosted（Remote Control／My Machines），coordinator 可把 worker 派到既有 checkout；這條還早，**只裝在本機的 MCP 給這些 worker 用，員工說團隊還在處理**。  
   為什麼值得記：這三則把「幾千個 subagent」從行銷句拆成可核對的產品限制。任何「planner 用貴模型、工人用便宜模型」或「本機 Projects 不碰雲」的演示，先問它有沒有獨立設定，還是只靠 prompt。

3. **員工再確認：Cloud MCP OAuth 的 `cursor://` 沒有 ETA；Grok Bot 連 IBKR 仍無通路**  
   來源：[論壇 167935](https://forum.cursor.com/t/mcp-oauth-still-uses-cursor-redirect-hubspot-and-other-http-s-only-providers-cannot-connect/167935)（deanrie 9/14 08:25 UTC）、[論壇 168052](https://forum.cursor.com/t/grok-bot-ibkr-mcp-oauth-fails-redirect-uri-works-on-grok-marketplace/168052)（mohitjain 9/14 10:35 UTC）。同窗口未回員工：[論壇 171680](https://forum.cursor.com/t/desktop-mcp-not-authenticating-for-live-meta-ads-mcp/171680)（Meta Live 拒 `http://localhost:8787/callback`，對方只准許 `www.cursor.com/agents/mcp/oauth/callback`）  
   主張：HubSpot 這類只准 HTTP(S) 的供應商，Cloud 流程仍回 `cursor://` 被拒；`localhost:8787` 本機註冊是對的，**無法用 `mcp.json` 強迫 Cloud redirect**。權宜不變：本機連、Cloud 先暫停。Grok Bot 只接 remote MCP，IBKR 在 Bot 裡沒有可用路徑；IDE 端仍是 stdio 橋（`npx mcp-remote https://api.ibkr.com/v1/api/mcp-public`）。兩邊都沒有時程。  
   為什麼值得記：上期只是 bump；今天員工把「不是你設錯、沒有 ETA」寫死。任何「一鍵連券商／HubSpot／Live Meta Ads」的雲端演示，先問 redirect 是 loopback、`cursor://`，還是 `cursor.com/agents/mcp/oauth/callback`。

5. **員工確認：個人 Pro 的 Bugbot 看的是 PR 作者帳號，不是「repo 已開啟」**  
   來源：[論壇 171633](https://forum.cursor.com/t/bugbot-says-disabled-for-this-repository-for-a-repo-the-dashboard-shows-as-enabled-while-approval-and-security-agents-run-on-it/171633)（deanrie 9/14 17:03 UTC；回報者 20:55 UTC 接受）  
   主張：儀表板顯示 repo 已開、Approval／Security Agent 都有 check run，Bugbot 仍說 `disabled for this repository`。原因：個人 Pro 只審「開啟 PR（或打 `bugbot run`）的 GitHub 使用者」所連結的那份 Cursor 帳號；工程師自己的帳號沒開這個 repo，就被跳過。文案會改。Approval／Security 走 installation owner，限制不同。回報者改完設定後通過。  
   為什麼值得記：這不是整合壞掉。團隊若用個人 Pro 當 Bugbot，儀表板綠燈 ≠ 每位作者都會被審。
