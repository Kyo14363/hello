# coding-agent-wind · 2026-09-28

今天沒有新的 changelog／blog／[@cursor_ai](https://x.com/cursor_ai) 產品官宣。窗口內最硬的是員工把幾條可複測的 agent／MCP 限制寫死：Grok Bot GitHub connector 大檔會寫進佔位字串、本機 MCP 共用行程 Refresh 不重載工具表、`Fallback Model Disabled` 其實是 Other Models 見底、以及 Agents 列的 zombie Working 是顯示問題。

1. **來源：** [論壇 173081](https://forum.cursor.com/t/grokbot-burns-token-because-tools-fail-to-pull-files/173081)（deanrie 07:41、16:16Z）  
   **主張：** Grok Bot 經 GitHub connector 寫檔時，**整份內容必須塞進單次 tool call**。大約 100KB 以上會被截斷，bot 改插入 `@file:/tmp/...` 或 `LOAD_FROM_FILE:...`，後面沒有東西展開，connector 就把佔位字串當正文 commit。HTTPS `git push` 另因環境預設沒有 GitHub username 而失敗（`could not read Username`）。員工確認這是根因，修補還沒出。現行 workaround：先 `gh auth login`（裝置碼＋核准卡），在磁碟上做小幅 targeted edit，再 `git add`／`commit`／`git push`；commit 前對每個改過的檔跑 `wc -c`，比原文小很多就停。失敗回合仍可能計費，要查帳寫 `hi@cursor.com`。  
   **為什麼值得記：** 「Grok Bot 幫你 push 大檔」的演示，先對磁碟／`git show HEAD:path` 的位元組數，不要信聊天裡的「已寫入」。佔位路徑在 agent VM 上，別台機器 pull 下來也展開不了。

2. **來源：** [論壇 173112](https://forum.cursor.com/t/changes-in-mcp-server-not-detected-until-cursor-restart/173112)（Colin 15:46Z）＋既有 [docs/context/mcp](https://cursor.com/docs/context/mcp)  
   **主張：** 本機 MCP 跑在**所有 Cursor 視窗共用的一個背景行程**。Refresh、或 Customize 裡關再開，都還是沿用先前載入的工具表；只關當前視窗不夠，要關光所有視窗才看得到新 endpoint。這是已知問題。不等重啟的 workaround：改那個 server 的 `mcp.json` 條目，讓 Cursor 當成新設定——stdio 就 bump dummy `"env": { "MCP_REV": "2" }`，URL server 就在 `url` 加 `?rev=2`。回報者在 **3.22.7**（commit `37076c6`，2026-09-24T05:01Z）。官方 FAQ 仍寫「自訂 server 改完要重啟 Cursor」，沒寫 Refresh 無效。  
   **為什麼值得記：** 任何「加了 MCP tool、agent 立刻看得到」的現場演示，先 bump config。工具列沒變，先當共用行程快取，不要當 server 沒 rebuild。

3. **來源：** [論壇 173080](https://forum.cursor.com/t/fallback-model-disabled/173080)（Colin 15:52Z）  
   **主張：** 使用者以為自己在跑 Grok 4.7 High，那則 chat **其實是 Claude Opus 5.5 Max**。第三方模型吃 Other Models 池，池在任務中途見底就停。Cursor 接著試圖自動切到 **Grok 4.6**；對方在 Models 裡關了 4.6，於是跳出 `The suggested fallback model is disabled`。員工承認這句沒解釋真因。繼續做的三條路：picker 改 Grok 4.7 High／Auto／Composer（吃還有餘額的 Cursor Models）、把 4.6 重新打開讓自動切換過、或在 dashboard Spending 開 on-demand。用量看 [cursor.com/dashboard](https://cursor.com/dashboard) 的兩個池。  
   **為什麼值得記：** 這把 9/25 Colin 在 [172889](https://forum.cursor.com/t/auto-usage-suddenly-reaching-100/172889) 寫的雙池溢流接到一條具體錯誤字串。長跑 agent 中途死掉，先對 Usage 兩個池和 Models 開關，不要當 4.7 當機。

4. **來源：** [論壇 173110](https://forum.cursor.com/t/finished-agents-still-show-as-working/173110)（Colin 15:47Z）  
   **主張：** Windows 上背景 subagent 的 transcript 已 `turn_ended: success`、聊天也寫「Worked for…」，Agents 側欄和 Working pill 仍顯示在跑。Stop、Stop All、Reload Window 都清不掉。員工確認**後面沒有活著的行程**，是先前「zombie Working」同一條顯示 bug；髒列綁在那個 parent chat。workaround：下一批判 subagent 開新 chat。員工在問：對卡住的 parent 丟一句短訊會不會清掉。回報者同樣是 3.22.7 Agent Window。  
   **為什麼值得記：** 「開了一群 audit worker、側欄還在 Working」不能當還在燒 token 的證據。要對 subagent transcript 的 `turn_ended`，不要對 pill。

5. **來源：** [論壇 173073](https://forum.cursor.com/t/1password-plugin-mcp-fails-to-start-spawn-1password-mcp-eacces/173073)（Colin 16:11Z，回報者 21:43Z 確認 Option 1 有效）＋ [論壇 173142](https://forum.cursor.com/t/grokbot-1password/173142)（Colin 19:55Z）  
   **主張：** Marketplace 1Password plugin 用 PATH 上的 `1password-mcp`。Mac 上若 `/usr/local/bin` 是 `drwx------`，Cursor 看進去就是 `EACCES`；spawn policy 寫 `sandboxed=false`，**不是 MCP sandbox**。修法：`sudo chmod 755 /usr/local/bin`（必要時 `chmod -h 755` 那個 symlink），或在 `~/.cursor/mcp.json` 寫絕對路徑 `/Applications/1Password.app/Contents/MacOS/1password-mcp` 並關掉 plugin 自己的 server；1Password Labs 的 MCP Server 也要開。Grok Bot 連同一套 1Password 時，共享 vault 裡**任何一筆 website 欄超過約 2,000 字元**（常見是帶長 redirect 的登入網址）會讓**整條連線**失敗，UI 只剩 generic「delivery outcome is unknown」。workaround：先清掉過長 URL，或暫時搬空 vault 再一筆筆加回。  
   **為什麼值得記：** 兩條都長得像「官方 1Password／MCP 壞了」。一條是本機目錄權限，一條是單筆超長欄位炸整 vault。演示前先 `ls -ld /usr/local/bin` 和檢查 website 欄長度。

6. **來源：** [論壇 173092](https://forum.cursor.com/t/github-allow-filtering-out-repositories-available-to-cursor-eg-by-github-org-or-individually/173092)（Colin 15:48Z）＋ [docs/enterprise/model-and-integration-management](https://cursor.com/docs/enterprise/model-and-integration-management)（Protected Git Scopes）＋ [論壇 170425](https://forum.cursor.com/t/local-agents-fail-to-start-while-cloud-agents-work-fine/170425)（deanrie 16:02Z）  
   **主張：** 同一個 GitHub 帳號掛個人＋公司兩套 Cursor 時，GitHub App 會把兩邊 repo 都列出來。今天能擋「個人帳號對公司 repo 開跑」的是 dashboard Integrations 的 **Protected Git Scopes**：公司 Cursor admin 且是 GitHub org admin 才能 claim；之後只有該 Cursor 團隊能對那些 repo 用 Cloud Agents／Automations／Bugbot，個人帳號開跑會被擋。兩個仍在的縫：claim 過的 repo **仍出現在個人帳號的 repo 清單**（只是開跑失敗）；**沒有**把個人 repo 從公司 picker 藏起來的開關。docs 寫 GitHub／GitLab 雲端與自架都適用。另：本機 Agent 的 shell／搜尋走預設 terminal profile；`.zshrc`／oh-my-zsh／banner 一慢，本機指令不回、chat 等到 timeout，**Cloud Agents 看起來卻正常**（工具在雲端機）。workaround：Default Profile 改 bash，或把 zsh 啟動變輕。  
   **為什麼值得記：** 「同一 GitHub、兩套 Cursor、不會點錯 repo」今天只保證公司側開跑被擋，清單仍會誘惑人。本機 agent 掛、雲端活著，先對 shell 啟動時間，不要當模型或帳號問題。
