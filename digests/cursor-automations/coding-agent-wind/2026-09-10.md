官方 changelog 與 [@cursor_ai](https://x.com/cursor_ai) 都沒有新帖，但員工今天把三件實作釘死：CLI MCP 改成按需載入、self-hosted `--data-dir` 已生效，以及「多倉 Environment」在 Linear／Automation 各卡一層。

1. **CLI MCP：員工說已改成按需載 schema，不再一次塞滿模型工具上限**  
   來源：[論壇 165642](https://forum.cursor.com/t/cli-mcp-tool-limits/165642)（員工 deanrie 9/9 07:43 UTC；原回報者 23:14 說會用最新 CLI 複測）  
   主張：7 月的 `Too many MCP tools are enabled for this model` 不是 CLI 另設上限，而是 CLI 開場就把全部 MCP schema 送進一次請求。員工今天說現行 CLI 已改成跟 app 一樣「用到才載」，Auto 加上整組已啟用 MCP 也不該再撞 per-model cap。回報者還補一句：遠端 workspace 的 MCP 登入仍比工具上限難搞。  
   為什麼值得記：這是近 24 小時最接近產品更新的員工宣告，但 changelog／[CLI changelog](https://cursor.com/docs/cli/changelog) 都沒寫；要自己核對 `agent --version`，不要只看論壇句子。

2. **Windows 3.19.13：員工把主題改成「Grep／本機檔案工具慢」，使用者量到 `LocalGrepExecutor.runFilesMode` 要半小時**  
   來源：[論壇 171047](https://forum.cursor.com/t/grep-file-based-tools-slow-on-windows-since-3-9-13/171047)（Colin 9/9 11:23 UTC 改名並說與模型無關；Florin 09:29 的 executor 數字；iochleonard 13:28 說降到 3.17 只好一小時）  
   主張：Grep／Search／Explore 是主要卡點。有人用 agent 自查：`LocalGrepExecutor.executeRg` 不到 2 秒，`runFilesMode` 卻到 1,834–1,846 秒。另一則 Windows 11 網域機在多 chat／subagent 時，shell／讀檔／terminal 每步 10–100 秒，renderer 一直打「extension host is unresponsive」，CPU profile 226 秒裡事件迴圈忙了 225.7 秒。降版不是穩定解法。  
   為什麼值得記：昨天是「模型幾秒就回、卡在本機 I/O」；今天有可對的 executor 名稱與秒數，hotfix 還沒出現。

3. **Self-hosted worker：`--data-dir` 已修，沒加旗標仍共用一把全域鎖**  
   來源：[論壇 167568](https://forum.cursor.com/t/regression-agent-worker-start-no-longer-works-per-repo-and-the-documented-data-dir-escape-hatch-is-also-broken/167568)（員工 kevinn 9/9 17:02 UTC）  
   主張：`agent worker --data-dir <path> start` 現在會生效；`CURSOR_DATA_DIR` 也還能用。在另一個 checkout 不帶旗標啟動，仍共用預設 data dir，第二個 worker 會撞 lock。若要一台機器服務多倉，改對每個 checkout 傳 `--worker-dir`。員工點名 2026.08.25 版已含 `--data-dir` 修復。  
   為什麼值得記：9/2 [Self-hosted machines](https://cursor.com/changelog/self-hosted-machines) 賣「一機一倉各自 `agent worker start`」；實作上預設仍是單 data dir，多倉要顯式隔離。

4. **多倉 Environment：Linear 指派永遠單倉；Automation「多選」選不到已包 Environment 的 repo**  
   來源：[論壇 171012](https://forum.cursor.com/t/linear-integration-creates-new-single-repo-environment-instead-of-using-prepared-multi-repo-environment/171012)（kevinn 9/9 01:19 UTC）、[論壇 171188](https://forum.cursor.com/t/multiple-repos-in-automations/171188)（kevinn 9/9 23:31 UTC）  
   主張：從 Linear 指派 Cursor 只看 `repo=`／label／Default Repository，然後用或新建單倉 Environment；不會去找已存的多倉 Environment。文件裡的 repo group 只在 web／API `repos`／Automation 自己指定那組倉時才算。另一邊，Automation「Select Multiple」把已有 saved Environment 的倉顯示成 Environment 列，而多選模式不能勾 Environment，所以那些倉變灰；沒包 Environment 的倉仍可勾。權宜：做一個包含所有倉的 Environment，或刪掉單倉 Environment 讓裸 repo 列回來。  
   為什麼值得記：這把「多倉 Cloud Agent」拆成兩條產品限制，不是 GitLab 配額也不是文件漏寫。
