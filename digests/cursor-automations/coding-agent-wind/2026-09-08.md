# coding-agent-wind｜2026-09-08

今天沒有夠硬的更新。官方 changelog、blog 與 [@cursor_ai](https://x.com/cursor_ai) 近 48 小時零發文，仍停在 9/2 Self-hosted Machines；近 24 小時能核對的是員工對公開 stream 競態、macOS computer-use 未修，以及 CLI／subagent 計費的落地限制。

1. **最接近一則（9/2 官方，非今日）**  
   來源：[Changelog · Self-hosted machines](https://cursor.com/changelog/self-hosted-machines)、[產品文](https://cursor.com/blog/self-hosted-machines)、[文件](https://cursor.com/docs/cloud-agent/self-hosted)  
   主張：Cloud Agent 的工具執行可放到自家機器或既有 sandbox（AWS Lambda、Cloudflare、Vercel、E2B 等）；推論與規劃仍在 Cursor。Linux／Mac worker 宣稱支援 computer use。  
   為什麼值得記：仍是最近可驗證的產品面更新。今天員工確認 macOS `--computer-use` 在現行 CLI 仍崩，代表「能跑在你機器上」與「desktop 真的能點」還不是同一件事。

2. **Cloud Agents 公開 stream：先連不上，連上了文字仍晚約 37 秒**  
   來源：[論壇 170833](https://forum.cursor.com/t/cloud-agents-api-sdk-stream-delivers-intermediate-messages-steps-20-40s-later-than-cursor-com-agents-ui-on-the-same-run/170833)（9/7 00:10 開；員工 Colin 13:21 UTC 回、回報者 18:51 複現）  
   主張：網頁 UI 與公開 run stream 讀同一條 live 事件，但 9/6 該帳號 53 次首次連線有 41 次立刻 `stream_unavailable`。`@cursor/sdk` 把 HTTP 409 當終態、`wait()` 報錯；若錯誤走 SSE，SDK 重連後一次回放，看起來像慢 20–40 秒。回報者照「約 1 秒再連」修好競態後，穩定 session 仍是 Get A Run `FINISHED` +31.2s、第一段 assistant SSE +68.6s（晚約 37 秒一次噴出）。  
   為什麼值得記：昨天還是單點觀察；今天有員工承認啟動競態，且「重連成功」仍無法對齊 UI。把 Cloud Agent 當產品後端時，問題在串流可用性，不是模型會不會寫程式。

3. **macOS `--computer-use`：員工確認 2026.09.02 仍崩、Intel／Apple Silicon 都中**  
   來源：[論壇 170703](https://forum.cursor.com/t/macos-self-hosted-worker-agent-worker-computer-use-start-crashes-at-startup/170703)（Colin 9/7 12:31 UTC）  
   主張：現行 CLI `2026.09.02-c22c1a3` 的 `agent worker --computer-use start` 仍會因 SEA `createRequire` 被關掉而退出。不加 `--computer-use` 的 worker 可跑。  
   為什麼值得記：從「使用者複現」變成官方承認未修；9/2 宣布的 Mac computer use 目前沒有可驗證 hotfix。

4. **CLI 卡在「Trusting workspace…」其實是 marketplace `git fetch` 堵住啟動**  
   來源：[論壇 170933](https://forum.cursor.com/t/cli-stuck-on-trusting-workspace-while-a-plugin-marketplace-git-fetch-blocks-startup/170933)（9/7 16:49；Colin 21:10 UTC）  
   主張：信任標記已寫入，UI 只是停在上一行；CLI 接著同步 plugin marketplace，每個 `git fetch` 完成前不出 prompt。空目錄、已信任目錄都中。員工說是已知問題，建議先設 `GIT_SSH_COMMAND` 讓死 SSH 約 30 秒失敗，而不是一直掛。CLI 版本同樣是 `2026.09.02-c22c1a3`。  
   為什麼值得記：可複現的啟動阻塞，不是氣氛文；coding agent CLI 的 marketplace 目前沒有「略過卡住的 plugin」開關。

5. **Subagent 顯示 Composer 2.5、帳單卻記 `composer-2.5-fast`**  
   來源：[論壇 170930](https://forum.cursor.com/t/billed-for-composer-2-5-fast-when-only-composer-2-5-is-selected/170930)（9/7 16:37；deanrie 17:40 UTC 確認，回報者 22:41 驗證 workaround）  
   主張：主 agent（Grok 4.6）生 Composer 2.5 subagent 時，子行程不繼承 Fast 開關，落到帳號對 Composer 2.5 的預設（新帳號預設 Fast on）。員工核過該 run。回報者把 Composer 2.5 的 Fast 手動開再開關後，新 subagent 列才變成 `composer-2.5`。這次用量在方案內額度，但 Fast 吃額度更快。  
   為什麼值得記：swarm／subagent 的「選了哪個模型」與「實際計哪一檔」可以不一致；看 [usage](https://cursor.com/dashboard/usage) 比看選擇器。

6. **Cua「現在可在 Win／Linux 跑 Cursor Cloud Agent」：文件比貼文窄**  
   來源：[Cua 貼文 9/7 17:50 UTC](https://x.com/trycua/status/2097019734919385176)（約 27 likes／1.9 萬曝光）、[Cua 操作指南](https://cua.ai/docs/how-to-guides/sandbox/run-cursor-cloud-agent-on-fleet)  
   主張：貼文寫 Windows 與 Linux 都能跑 Cursor Cloud Agent worker。指南本體是 Ubuntu 24.04 桌面映像、Enterprise + Team Pool + service-account key，本地 Python controller 必須一直佔住 Cua claim；並寫明「這是手動整合，不是 Cursor 內建 provider」，自動依 pending queue 擴縮要另寫控制器。Cursor 文件仍把 Cua 列在 partner／參考架構，不是一鍵開關。  
   為什麼值得記：這是今日 X 上最高互動的「可驗證演示」候選，但可重跑的是 Linux + 自管 controller，不是官方新 changelog。近 24 小時 X 上 Cursor+(agent|MCP|cloud agent) 約 589 則（昨天同條件約 322），多數是氣氛與 Grok Bot，不是新品。
